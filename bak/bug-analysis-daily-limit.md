# Bug 分析报告：每日学习上限配置未生效

## 一、Bug 描述

```
Bug ID: #1
发现时间: 2024-04-25
发现方式: E2E 测试 4 - 新手每日学习上限

问题：
├─ 用户可以设置每日学习上限（dailyLimitConfigAtom）
├─ 设置页面 UI 正常显示配置值
├─ 但实际学习中配置未生效
└─ 系统始终使用硬编码值 20
```

---

## 二、代码架构断裂分析

```
代码调用链：

┌─────────────────────────────────────────────────────────────────┐
│  设置页面 (AdvancedSetting.tsx)                                  │
│  ├─ 用户设置每日上限：10/20/30 等                                 │
│  ├─ 保存到 dailyLimitConfigAtom                                  │
│  └─ UI 显示：{dailyLimitConfig.dailyLimit} 个/天                 │
└─────────────────────────────────────────────────────────────────┘
                              ↓
                    dailyLimitConfigAtom
                              ↓
                    [断裂！配置到这里就断了]
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│  学习逻辑 (strategies.ts)                                        │
│  ├─ getWordNames() 硬编码：20                                    │
│  ├─ getNewWords(dictId, wordList, 20)                            │
│  ├─ getDueWords(dictId, wordList, 20)                            │
│  └─ [从未读取 dailyLimitConfigAtom]                              │
└─────────────────────────────────────────────────────────────────┘
                              ↓
                    用户实际学习：固定 20 个
```

**结论**：设置功能和实际功能之间没有连接。

## 三、问题位置

```
文件: src/pages/Typing/hooks/useLearningSession/strategies.ts
函数: normalStrategy.getWordNames()
行号: 16-22

问题代码:
```typescript
export const normalStrategy: WordSourceStrategy = {
  getWordNames(dictId: string, wordList: string[]): string[] {
    const dueWords = getDueWords(dictId, wordList, 20)  // 硬编码 20
    if (dueWords.length > 0) {
      return dueWords
    }
    return getNewWords(dictId, wordList, 20)  // 硬编码 20
  },
}
```

## 四、单元测试为何没测出

### 4.1 测试代码分析

```
文件: src/pages/Typing/hooks/useLearningSession/strategies.test.ts
测试: 第 57-61 行

测试代码:
```typescript
it('应该限制返回数量为20个', () => {
  const manyWords = Array.from({ length: 30 }, (_, i) => `word${i}`)
  const result = normalStrategy.getWordNames(dictId, manyWords)
  expect(result).toHaveLength(20)  // 问题在这里
})
```

### 4.2 测试设计问题

```
问题 1: 测试标题描述实现，不是需求
├─ 标题："应该限制返回数量为20个"
├─ 这是描述当前代码行为，不是业务需求
├─ 正确需求："应该使用用户配置的每日上限"
└─ 标题暗示"20是正确的"，没问"20从哪里来"

问题 2: 期望值 = 硬编码值
├─ 代码写 20
├─ 测试期望 20
├─ 期望值和实现值相同
└─ 无论代码正确与否，测试都通过

问题 3: 没有测试配置读取
├─ 没有设置 dailyLimitConfig = 5
├─ 没有验证是否读取配置
├─ 配置读取路径从未被覆盖
└─ 测试只测了默认值路径
```

### 4.3 测试覆盖盲区

```
grep 搜索结果:
├─ 单元测试中没有 dailyLimit 相关测试
├─ dailyLimitConfigAtom 定义了 (store/index.ts)
├─ AdvancedSetting 有 UI 设置
└─ 但 strategies.ts 没读取 → 没测试验证连接
```

## 五、根本原因总结

```
┌─────────────────────────────────────────────────────────────────┐
│  原因 1: 需求理解偏差                                            │
│  ├─ 需求：每日上限可配置                                          │
│  ├─ 实现：硬编码为 20                                             │
│  ├─ 开发可能理解为"默认20，暂时不实现可配置"                       │
│  └─ 但 UI 已经有配置功能，形成矛盾                                 │
│                                                                 │
│  原因 2: 测试跟随实现                                            │
│  ├─ 开发写代码 → 看返回什么值                                      │
│  ├─ 测试写断言 → 期望就是这个值                                    │
│  ├─ 没有问：这个值应该是从哪里来？                                 │
│  └─ 测试验证"代码做了什么"，没验证"代码应该做什么"                  │
│                                                                 │
│  原因 3: 架构断裂未被发现                                         │
│  ├─ 设置页面 → 配置存储 → [断裂] → 学习逻辑                        │
│  ├─ 单元测试只测学习逻辑，不测配置连接                             │
│  ├─ 集成测试缺失：没有测试设置→生效的完整流程                      │
│  └─ E2E 测试才能发现这种断裂                                      │
│                                                                 │
│  原因 4: 测试层级不足                                            │
│  ├─ 只有单元测试（测函数内部）                                     │
│  ├─ 缺少集成测试（测模块连接）                                     │
│  └─ 完整流程 bug 需要更高层级测试                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 七、下次避免方法

```
┌─────────────────────────────────────────────────────────────────┐
│  方法 1: 测试先问"值从哪里来"                                     │
│  ├─ 写测试前，先画数据流图                                        │
│  ├─ 问：这个值是硬编码？还是配置？                                 │
│  ├─ 如果是配置：必须测试配置读取                                   │
│  └─ 示例：                                                        │
│      - dailyLimit 从 dailyLimitConfigAtom 来                     │
│      - 测试必须设置配置并验证生效                                  │
│                                                                 │
│  方法 2: 每个可配置项必须有完整测试                                │
│  ├─ 测试A：设置配置值X，验证行为符合X                             │
│  ├─ 测试B：设置配置值Y，验证行为符合Y                             │
│  ├─ 测试C：不设置配置，验证使用默认值                              │
│  └─ 三个测试覆盖所有路径                                          │
│                                                                 │
│  方法 3: 单元测试 + 集成测试组合                                   │
│  ├─ 单元测试：测函数内部逻辑                                       │
│  ├─ 集成测试：测模块间连接                                         │
│  ├─ E2E测试：测完整用户流程                                       │
│  └─ 本bug需要集成测试或E2E才能发现                                 │
│                                                                 │
│  方法 4: 需求文档 → 测试设计 → 代码实现                            │
│  ├─ 先写需求：每日上限可配置（5-100）                              │
│  ├─ 再写测试：设置5验证5，设置30验证30                             │
│  ├─ 最后写代码：读取配置并实现                                     │
│  └─ 不是反过来：代码 → 测试 → 需求                                 │
│                                                                 │
│  方法 5: 代码审查检查配置连接                                      │
│  ├─ 发现新配置项时，检查是否被使用                                 │
│  ├─ dailyLimitConfigAtom 定义了                                   │
│  ├─ 问：哪些地方使用了它？                                         │
│  ├─ 答：只有 AdvancedSetting                                      │
│  └─ 结论：学习逻辑没使用 → 发现bug                                 │
└─────────────────────────────────────────────────────────────────┘
```
